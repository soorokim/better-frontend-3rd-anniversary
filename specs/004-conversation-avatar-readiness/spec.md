# Feature Specification: 대화 아바타 배포 준비

**Feature Branch**: `codex/conversation-avatar`

**Created**: 2026-08-30

**Status**: Draft

**Input**: User description: "대화 아바타 작업을 현재 서비스에 안전하게 합치고, 브랜치 전달 누락과 데이터 변경 순서 충돌을 없앤다. 승인 별칭은 가입·로그인·PIN 초기화에서 똑같이 동작해야 하며, 가입 요청의 과도한 연산을 제한하고 공개 연출을 보조기술에서도 무리 없이 이용할 수 있게 한다. 통합·브라우저·깨끗한 서버 설치 검증을 끝내 배포 가능한 상태로 만든다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 현재 서비스에 빠짐없이 합치기 (Priority: P1)

운영자는 이미 사용 중인 질문·답변·진행자 화면을 유지하면서 대화 아바타 기능을 배포한다. 다른 작업자가 같은 변경본을 받아도 로컬에서만 남은 파일 없이 동일한 기능과 문서를 확인할 수 있고, 기존 데이터 변경 다음 순서로 새 변경이 한 번씩 적용된다.

**Why this priority**: 변경본과 데이터 변경 순서가 재현되지 않으면 다른 기능을 아무리 고쳐도 서버에 올릴 수 없다.

**Independent Test**: 기존 서비스 데이터가 있는 환경과 비어 있는 환경에 같은 변경본을 적용하고, 기존 진행자 기능과 새 대화 아바타 기능을 모두 사용할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 현재 운영 기준선에 질문·답변·진행자 기능이 있는 상태, **When** 대화 아바타 변경본을 적용하면, **Then** 기존 기능이 사라지지 않고 대화 아바타 기능이 함께 제공된다.
2. **Given** 이전 데이터 변경이 이미 적용된 서버, **When** 새 데이터 변경을 적용하면, **Then** 순서 충돌이나 중복 실행 없이 필요한 구조만 한 번 추가된다.
3. **Given** 저장소를 처음 받은 작업자 또는 자동화 도구, **When** 문서의 설치 절차를 따르면, **Then** 별도의 로컬 파일 전달 없이 동일한 서비스를 실행할 수 있다.
4. **Given** 배포 전 변경 집합, **When** 추적되지 않은 필수 파일과 기준선 차이를 검사하면, **Then** 기능에 필요한 코드·명세·검증 자료가 모두 변경 집합에 포함되어 있다.

### User Story 2 - 어떤 승인 닉네임으로도 계정 복구하기 (Priority: P1)

참가자는 가입할 때 사용한 정식 닉네임이나 승인 별칭을 로그인과 PIN 초기화에서도 그대로 쓸 수 있다. 화면마다 다른 닉네임을 기억할 필요가 없어야 한다.

**Why this priority**: 행사 당일 PIN을 잊은 사람이 관리자의 초기화 코드를 받아도 계정으로 돌아오지 못하면 진행 흐름이 멈춘다.

**Independent Test**: 승인 별칭으로 가입한 참가자의 PIN을 관리자가 초기화한 뒤 같은 별칭과 새 PIN으로 로그인해 기존 답변과 확정 아바타가 유지되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정식 닉네임과 하나 이상의 승인 별칭이 연결된 참가자, **When** 어느 승인 이름으로 PIN 초기화를 완료하면, **Then** 같은 계정의 PIN이 변경된다.
2. **Given** PIN이 초기화된 참가자, **When** 가입 때 사용한 별칭과 새 PIN으로 로그인하면, **Then** 기존 계정·답변·확정 아바타로 돌아간다.
3. **Given** 승인되지 않은 이름이나 다른 참가자에게 연결된 이름, **When** PIN 초기화를 시도하면, **Then** 계정 존재 여부를 드러내지 않는 동일한 실패 안내를 받고 아무 계정도 변경되지 않는다.

### User Story 3 - 반복 가입 요청에도 행사 서비스 유지하기 (Priority: P2)

운영자는 초대 코드가 참가자 사이에 공유된 뒤에도 잘못된 닉네임을 반복 제출하는 요청 때문에 정상 참가자의 가입이 느려지지 않기를 원한다. 정상적인 가입은 빠르게 끝나고, 반복 요청은 잠시 제한된다는 안내를 받아야 한다.

**Why this priority**: 공통 초대 코드는 비밀 관리자 암호가 아니므로, 유효한 초대 코드를 가진 요청도 서버 자원을 무제한 사용할 수 있게 두면 안 된다.

**Independent Test**: 한 출처에서 잘못된 닉네임으로 가입을 반복한 뒤 제한 여부와 정상적인 다른 참가자의 가입 시간을 함께 확인한다.

**Acceptance Scenarios**:

1. **Given** 유효한 초대 코드와 승인되지 않은 닉네임, **When** 가입을 반복 요청하면, **Then** 계정이나 인증 정보가 생기지 않고 정해진 횟수 뒤 잠시 제한된다.
2. **Given** 한 출처가 제한된 상태, **When** 다른 정상 참가자가 승인 닉네임으로 가입하면, **Then** 영향을 받지 않고 가입을 완료한다.
3. **Given** 승인 닉네임의 정상 가입, **When** 요청이 처리되면, **Then** 사용자는 2초 안에 다음 화면으로 이동할 수 있다.

### User Story 4 - 보조기술에서도 편안하게 캐릭터 확인하기 (Priority: P2)

움직임 축소 설정이나 스크린리더를 사용하는 참가자도 반복 안내에 방해받지 않고 확정 캐릭터와 개발자 프로필을 확인한다. 시각적인 셔플 연출은 유지하되 핵심 결과를 이해하는 데 꼭 필요하지 않아야 한다.

**Why this priority**: 캐릭터 공개는 참가자 모두가 거치는 첫 경험이라서 특정 입력 방식이나 감각에 과한 부담을 주면 안 된다.

**Independent Test**: 움직임 축소와 스크린리더 안내를 각각 켜고 가입부터 확정 카드 확인까지 진행해, 짧고 의미 있는 상태 안내만 제공되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 움직임 축소를 사용하는 참가자, **When** 캐릭터 공개 화면에 들어가면, **Then** 빠르게 교체되는 후보 없이 확정 결과를 1초 안에 확인한다.
2. **Given** 스크린리더를 사용하는 참가자, **When** 일반 공개 연출이 진행되면, **Then** 반복되는 후보 문구 전체가 계속 읽히지 않고 준비 시작과 완료 상태를 분명히 알 수 있다.
3. **Given** 키보드만 사용하는 참가자, **When** 확정 카드와 상태 변경 동작을 이용하면, **Then** 모든 동작에 도달하고 현재 상태를 알 수 있다.

### Edge Cases

- 기존 서버에는 앞선 데이터 변경이 적용되어 있지만 새 서버에는 아무 데이터도 없을 수 있다.
- 변경 적용 도중 실패하거나 서버가 재시작되어도 기존 질문·답변·진행 상태를 잃지 않아야 한다.
- 같은 참가자에게 연결된 정식 닉네임과 별칭이 공백·대소문자·특수문자 정규화 뒤 겹칠 수 있다.
- 한 참가자의 별칭이 잘못해서 다른 참가자에게도 연결된 경우 자동으로 계정을 선택하지 않아야 한다.
- 반복 가입 제한이 정상 참가자 전체를 한꺼번에 막아서는 안 된다.
- 캐릭터 공개 도중 새로고침하거나 재접속해도 계정과 확정 아바타가 중복 생성되지 않아야 한다.
- 공개 연출 중 후보가 자주 바뀌더라도 보조기술용 안내는 과도하게 반복되지 않아야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 대화 아바타 기능에 필요한 모든 코드, 명세, 검증 자료와 운영 문서를 하나의 전달 가능한 변경 집합으로 제공해야 한다.
- **FR-002**: 시스템은 현재 서비스의 기존 질문·답변·관리자·진행자 기능을 유지한 채 대화 아바타 기능을 함께 제공해야 한다.
- **FR-003**: 시스템은 기존 서버와 새 서버 모두에서 데이터 변경을 정해진 순서대로 한 번씩 적용하고, 이름이나 순서가 겹치는 변경을 허용하지 않아야 한다.
- **FR-004**: 시스템은 데이터 변경 실패 시 기존 운영 데이터를 보존하고, 운영자가 백업에서 복구하거나 안전하게 다시 시도할 수 있는 절차를 제공해야 한다.
- **FR-005**: 시스템은 정식 닉네임과 승인 별칭을 가입, 로그인, PIN 초기화에서 동일한 규칙으로 한 참가자 계정에 연결해야 한다.
- **FR-006**: 시스템은 승인되지 않았거나 둘 이상의 계정과 충돌하는 이름으로 인증 또는 PIN 초기화를 시도할 때 어떤 계정도 선택하거나 변경하지 않아야 한다.
- **FR-007**: PIN 초기화 뒤에도 참가자의 계정 식별자, 답변, 확정 아바타와 프로필 연결은 유지되어야 한다.
- **FR-008**: 시스템은 가입 요청의 닉네임 승인 여부를 확인하기 전에 불필요하게 비용이 큰 인증 정보 처리를 반복하지 않아야 한다.
- **FR-009**: 시스템은 유효한 초대 코드를 포함한 반복 가입 요청도 출처와 대상 이름을 고려해 제한하고, 정상적인 다른 참가자의 가입을 함께 차단하지 않아야 한다.
- **FR-010**: 반복 요청이 제한된 사용자는 기다린 뒤 다시 시도할 수 있다는 안내와 남은 대기 정보를 받아야 한다.
- **FR-011**: 움직임 축소를 요청한 참가자에게는 빠른 후보 교체 없이 확정 프로필을 1초 안에 표시해야 한다.
- **FR-012**: 스크린리더용 공개 상태는 준비 시작과 완료처럼 의미 있는 변화만 안내하고, 빠르게 교체되는 장식용 후보를 매번 읽지 않아야 한다.
- **FR-013**: 확정 프로필의 주요 정보와 상호작용은 모바일, 터치, 키보드와 보조기술에서 사용할 수 있어야 한다.
- **FR-014**: 시스템은 기존 서비스와 대화 아바타 기능의 대표 흐름, 별칭 PIN 복구, 반복 요청 제한, 접근성 동작을 자동 검증할 수 있어야 한다.
- **FR-015**: 배포 안내서는 깨끗한 서버 설치, 기존 서버 갱신, 데이터 백업·복구와 실패 후 재시도 절차를 구분해 설명해야 한다.
- **FR-016**: 배포 후보는 로컬에만 존재하는 필수 파일, 미완료 핵심 검증, 알려진 데이터 변경 충돌이 없는 상태여야 한다.
- **FR-017**: 이 구간은 대화 분석 규칙이나 캐릭터 조합 종류를 새로 확장하지 않고, 기존 대화 아바타 결과의 안전한 통합과 운영 준비에만 집중해야 한다.

### Key Entities

- **배포 변경 집합**: 다른 작업자와 서버가 같은 결과를 재현하는 데 필요한 코드, 명세, 검증 자료와 문서의 묶음이다.
- **데이터 변경 단계**: 기존 서비스 구조 다음에 적용되는 순서가 있는 변경이며, 적용 여부와 실패 시 복구 기준을 가진다.
- **참가자 이름 연결**: 한 참가자 계정과 정식 닉네임, 승인 별칭 사이의 유일한 관계다.
- **가입 시도 상태**: 반복 가입 요청을 구분하기 위한 대상과 출처, 실패 횟수, 제한 만료 시점을 나타낸다.
- **공개 안내 상태**: 보조기술에 전달되는 준비 시작, 완료와 최종 프로필 상태다.
- **배포 검증 기록**: 깨끗한 설치와 기존 서버 갱신에서 어떤 시나리오가 언제 성공했는지 남기는 민감정보 없는 결과다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 새 작업자가 전달된 변경 집합만 받아 문서대로 실행했을 때 30분 안에 기존 기능과 대화 아바타 기능을 함께 실행한다.
- **SC-002**: 깨끗한 환경과 기존 운영 구조가 있는 환경에서 데이터 변경을 각각 3회 검증했을 때 순서 충돌, 중복 적용, 기존 기능 손실이 0건이다.
- **SC-003**: 정식 닉네임과 승인 별칭 각각으로 가입, 로그인, PIN 초기화 시나리오를 반복했을 때 같은 계정으로 복구되는 비율이 100%다.
- **SC-004**: 승인되지 않거나 충돌하는 이름으로 PIN 초기화를 20회 시도했을 때 변경된 계정과 노출된 계정 식별 정보가 0건이다.
- **SC-005**: 한 출처에서 잘못된 가입을 반복하면 정해진 한도 안에서 제한되고, 동시에 진행한 다른 정상 참가자 20명의 가입 성공률은 100%다.
- **SC-006**: 정상 가입 요청의 95%에서 사용자는 2초 안에 다음 화면으로 이동한다.
- **SC-007**: 움직임 축소 환경에서 공개 화면 20회 중 확정 프로필이 1초 안에 표시되는 비율이 100%다.
- **SC-008**: 스크린리더 검증에서 빠르게 변하는 후보 문구의 반복 낭독이 0회이고, 준비 시작과 완료 안내를 각각 한 번 이하로 듣는다.
- **SC-009**: 모바일 360px, 터치, 키보드 전용, 고대비와 움직임 축소 환경에서 핵심 참가자 흐름의 완료율이 100%다.
- **SC-010**: 배포 전 필수 검증을 모두 실행했을 때 실패 항목, 미추적 필수 파일과 알려진 차단 문제가 0건이다.

## Assumptions

- `003` 대화 아바타 기능의 사용자 경험과 분석 결과 형식은 이미 승인되었으며 이번 구간에서는 바꾸지 않는다.
- 현재 운영 기준선에는 질문·답변과 진행자 결과 화면이 포함되어 있고, 대화 아바타 기능은 그 위에 추가된다.
- 정식 닉네임과 승인 별칭은 운영자가 검토한 활성 프로필 명단을 기준으로 한다.
- 반복 요청 제한은 개인 참가자 단위에 가깝게 적용하며 행사 전체를 막는 전역 제한은 사용하지 않는다.
- 데이터 삭제나 초기화 없이 전진 적용하는 것을 기본으로 하고, 실패 시에는 적용 전 백업으로 복구한다.
- 실제 카카오 대화 원문과 원본 사용자 식별자는 기존 개인정보 경계를 그대로 지키며 이 구간의 변경 집합에 포함하지 않는다.

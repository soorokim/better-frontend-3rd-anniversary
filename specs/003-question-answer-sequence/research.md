# Research: 질문별 답변 공개 진행

## Decision 1: 행사별 진행 포인터를 질문별 발표 세션과 분리

**Decision**: `question_sequence_sessions`를 행사당 하나 만들고, 현재 질문·현재 단계·revision·완료
시각을 저장한다. 기존 `presentation_sessions`는 질문별 답변 발표 기록으로 유지한다.

**Rationale**: 기존 발표 세션은 질문 안에서 답변을 고르는 기록에는 맞지만, 네 질문의 순서와
다음 질문 전환을 원자적으로 관리할 자리가 없다. 행사 진행 포인터를 잠그면 두 진행자 창이
동시에 다음 질문을 눌러도 한 번만 전환되고, 아직 열지 않은 질문을 화면에 보내지 않을 수 있다.

**Alternatives considered**:

- 질문 행에 현재 여부를 직접 넣는 방식은 각 질문의 공개 상태와 전체 진행 위치가 섞여 이전
  질문 재확인 시 규칙이 흐려진다.
- 브라우저 상태로 순서를 관리하면 새로고침·재배포 복구 조건을 만족하지 못한다.

## Decision 2: 네 질문은 행사 초기화 때 모두 생성하고 순서는 저장소가 보장

**Decision**: `questions`에 행사 안의 고정 순서를 나타내는 `display_order`를 추가하고,
`(event_id, display_order)`를 유일하게 만든다. 시드 데이터는 네 질문을 한 번에 만들고 행사 전
모두 참가자 답변 가능 상태로 둔다. 발표 순서는 QuestionSequenceSession만 관리하며 질문 전환이
참가자 답변 가능 여부를 바꾸지 않는다.

**Rationale**: 참가자가 행사 전 네 질문에 모두 답할 수 있어야 행사 당일에는 답을 받지 않고
공개만 할 수 있다. 질문 문구와 순서는 미리 저장해 두므로 행사 중에는 진행자가 순서를 입력할
필요가 없다.

**Alternatives considered**:

- 행사 중 질문이 열릴 때마다 답변을 받는 방식은 답변 수집 시간과 발표 시간이 섞여 사용자
  요구와 맞지 않는다.
- 질문 문구와 순서를 코드에만 두면 운영 DB를 백업·복구했을 때 행사 기록의 의미가 약해진다.

## Decision 3: 답변 항목은 작성자 공개 또는 명시적 제외 뒤에만 완료

**Decision**: `presentation_items`에 `completion_state`(`presenting`, `revealed`, `excluded`)와
완료 시각을 추가한다. 새 답변을 선택하면 `presenting`, 작성자 공개 명령이 성공하면
`revealed`, 진행자의 확인된 제외 명령이면 `excluded`가 된다. 다음 답변과 다음 질문 전환은
현재 항목이 `revealed` 또는 `excluded`일 때만 허용한다.

**Rationale**: 기존에는 항목이 생성된 순간 공개 완료로 간주했다. 그 방식은 답변만 보여 주고
작성자를 공개하지 않은 상태에서 다음으로 넘어가는 문제를 만들 수 있다. 명시적 상태가 있으면
요구한 `답변 공개 → 작성자 공개`가 저장소에서도 지켜진다.

**Alternatives considered**:

- `author_revealed` 한 값만 세션에 두면 과거 항목이 완료됐는지와 제외됐는지 알 수 없다.
- 제외한 답변을 원본에서 지우면 참가자 기록 불변 조건을 어긴다.

## Decision 4: 기존 2초 조회와 화면별 최소 DTO를 그대로 사용

**Decision**: 진행자·프로젝터는 2초 정기 조회와 `revision`을 계속 사용한다. 진행자 DTO는
네 질문의 locked/current/completed 상태와 남은 답변 수를 포함한다. 프로젝터 DTO는 현재
질문, 현재 답변과 공개가 끝난 작성자만 포함하며, 아직 열지 않은 질문·답변 목록은 보내지 않는다.
행사 완료 뒤 별도 참가자 기록 DTO가 네 질문의 공개 답변·작성자를 반환한다.

**Rationale**: 최대 30명 규모의 행사에서 2초 조회는 5초 반영 목표에 충분하고, 별도 실시간
서버의 연결·재연결 부담을 만들지 않는다. 기존 익명 DTO 분리는 작성자 정보가 DOM이나 응답에
섞이는 사고도 막는다.

**Alternatives considered**:

- WebSocket이나 SSE는 이번 규모에서 필요한 것보다 운영 복잡성이 크다.
- 하나의 큰 DTO를 두 화면이 공유하면 아직 공개하지 않은 답변·작성자 정보가 프로젝터에
  전달될 수 있다.

## Decision 5: 전체 완료 뒤에만 참가자 질답 기록을 연다

**Decision**: 참가자 인증을 확인하는 읽기 전용 질답 기록 route와 화면을 추가한다. 행사 진행
상태가 `completed`가 아니면 답변 목록을 반환하지 않고, 완료 뒤에는 질문 순서와 작성자가
공개된 답변 스냅샷만 반환한다.

**Rationale**: 행사 중에는 아직 공개하지 않은 내용이 퍼지지 않으면서, 끝난 뒤에는 별도 링크나
외부 공개 없이 모임 구성원이 전체 대화를 다시 볼 수 있다.

**Alternatives considered**:

- 행사 시작부터 참가자끼리 답변을 보게 하면 발표 순서와 익명 공개의 의미가 없어진다.
- 로그인 없는 공개 링크는 초대받지 않은 사람에게 기록이 퍼질 위험과 회수 정책을 만든다.

## Decision 6: 상태 변경은 행사 진행 행과 질문 세션을 함께 잠근다

**Decision**: `start_question`, `reveal_next_answer`, `reveal_author`, `exclude_current_answer`,
`advance_question`, `review_question` 명령을 allowlist로 제한한다. 명령은 행사 진행 행을 먼저
`FOR UPDATE`로 잠그고, 필요하면 대상 질문의 발표 세션도 잠근 뒤 완료 판정·전환·revision
증가를 한 트랜잭션으로 끝낸다.

**Rationale**: 동시 명령에서 질문 건너뛰기, 동일 답변 이중 선택, 작성자 공개 전 전환을
막는다. 기존 관리자 인증·CSRF 검증과 원본 답변 스냅샷 규칙도 그대로 재사용할 수 있다.

**Alternatives considered**:

- 화면에서 버튼을 비활성화하는 것만으로는 두 브라우저 창의 동시 요청을 막지 못한다.
- 임의 필드를 받는 PATCH는 불가능한 상태 조합을 만들기 쉽다.

## Decision 7: 검증은 상태 전이, 서버 경계, 두 화면 흐름으로 나눈다

**Decision**: 단위 테스트는 완료 상태와 DTO 익명화를, 통합 테스트는 실제 PostgreSQL 잠금과
권한·CSRF·전환 게이트를, Playwright는 1번부터 4번 질문까지의 두 화면 흐름과 새로고침 복구를
검증한다.

**Rationale**: 질문 순서 규칙은 빠른 단위 테스트로, 저장소 원자성은 통합 테스트로, 실제
프로젝터 갱신과 접근성은 브라우저에서 확인하는 편이 실패 원인을 찾기 쉽다.

**Alternatives considered**:

- 모든 조건을 E2E에만 넣으면 동시성·권한 실패 원인을 분리하기 어렵다.
- 단위 테스트만으로는 영속성, 인증, 두 창 동기화를 증명할 수 없다.

# Phase 0 Research: 대화 기반 개발자 아바타

## 1. 분석 대상의 범위

**Decision**: `users.is_system=0` 이고 `message_count>0`인 아카이브 사용자 전원을
분석한다. 기존 수동 명단은 필터가 아니라 운영자가 승인한 닉네임 변경 이력을 한 사람으로
병합하는 우선 규칙으로만 쓴다. 나머지 고유 닉네임 사용자는 자동 포함하지만 가입과 동일한
Unicode NFKC·대소문자·기호 정규화 키가 같은 원본 사용자 행이 둘 이상이면 자동 병합하지
않고 아카이브 안의 별도 검토 목록으로 출력한다. 운영자가 같은 사람인지 확인한 경우에만
Git에 포함되지 않는 서버 전용 별칭 규칙의 원본 user ID 목록으로 병합을 승인한다. 다른
사람이면 user ID별 행사 가입 닉네임을 지정한다. 깨끗한 행사 서버 전달물에는 user ID를
빼고 승인된 별칭과 원본 행 개수만 남긴다.

**Rationale**: 한 사람의 닉네임 변경을 여러 프로필로 나누지 않으면서도, 명단에
없던 대화 참여자를 빠뜨리지 않는다. 동시에 같은 정규화 이름을 우연히 쓴 다른 사람의
대화를 합치는 일을 막는다. 가입을 열기 전에 원본 `users` 수, 별칭 병합 후 프로필 수,
승인 대기 목록과 실제 병합 내역을 확인할 수 있다.

**Alternatives considered**:

- 수동 명단에 적힌 사람만 분석: 사용자가 원한 전원 사전 분석을 충족하지 못한다.
- 모든 `users` 행을 그대로 사용: 시스템 계정·메시지 0명·같은 사람의 승인된 별칭이 섞인다.
- 정확한 정규화 키가 같으면 자동 병합: 다른 사람을 한 계정으로 합칠 수 있어 운영자가 별칭 규칙에 승인한 경우만 병합한다.

## 2. 사전 배치와 읽기 전용 SQLite

**Decision**: 분석은 가입 요청과 분리한 일회성 Python CLI로 실행한다. SQLite는
`file:...?mode=ro` URI로 열고 `users`, `messages`, `links`, `attachments`를 읽는다.
가입 중에는 이 CLI를 호출하지 않는다.

**Rationale**: Python `sqlite3` URI는 `uri=True`일 때 SQLite URI 매개변수를 전달할 수
있다. 원본을 읽기 전용으로 열면 분석 스크립트가 아카이브를 수정하는 경로를 줄일 수
있다. 약 46만 건은 메시지 커서를 순차 순회하면 복잡한 분산 작업 없이 처리할
수 있는 규모다.

**Alternatives considered**:

- 가입 시 실시간 분석: 요청 타임아웃과 아카이브 가용성이 가입에 전파된다.
- 아카이브 DB 사본을 앱 서버로 복사: 원문 반출 금지 원칙에 어긋난다.
- 큐+SSE: 실제 분석을 사전에 끝내므로 추가 서비스와 장애 지점만 늘어난다.

**Sources**:

- https://docs.python.org/3/library/sqlite3.html#how-to-work-with-sqlite-uris

## 3. 원문 비반출과 안정적인 표식자

**Decision**: 개인별 표식자는 아카이브 환경의 별도 `AVATAR_HASH_KEY`로 메시지 ID,
날짜, 시간, 정규화된 본문 순서에 HMAC-SHA-256을 누적해 만든다. JSON에는 요약
통계, 상대 신호, 형용사·명사 후보, HMAC 결과만 썼다. 원문과 비밀값은 쓰지 않는다.

**Rationale**: 키가 없는 일반 해시는 입력 후보가 있는 경우 역추정에 약하다. HMAC는
비밀 키를 필요로 하고, Python 표준 라이브러리가 누적 `update()`와 표준 표현인
`hexdigest()`를 제공한다.

**Alternatives considered**:

- SHA-256(원문): 키 없이 유출된 표식자를 검증할 수 있다.
- 닉네임 해시: 대화 변화를 반영하지 못하고 기존 임시 아바타와 다를 바 없다.
- 원문 암호화 반출: 복호화 가능한 민감 데이터를 앱 서버에 추가하게 된다.

**Sources**:

- https://docs.python.org/3/library/hmac.html

## 4. 전원 산출물의 검증과 원자적 import

**Decision**: JSON 산출물에 스키마 버전, 선택 모드, 원본 user 행 수, 별칭 병합 후
프로필 수, 미매칭 목록, 중복 정규화 키 검토 목록, 개인별 원본 별칭을 포함한다.
원본 행 수와 프로필 수는 같을 필요가 없고, 각 원본 행이 프로필 또는 검토 목록에 정확히
한 번 포함되는지를 확인한다. import는 검토 목록이 비어 있는 JSON 전체를
검증한 뒤 하나의 PostgreSQL 트랜잭션으로 배치·프로필·별칭을 저장하고,
모든 고유성 조건을 통과했을 때만 새 배치를 활성화한다.

**Rationale**: 일부 프로필만 새 버전으로 들어가면 가입 허용 목록과 아바타 버전이
섞인다. Drizzle의 트랜잭션 범위에서 검증·저장·활성화를 함께 둘 수 있다.

**Alternatives considered**:

- 프로필별 upsert 후 개수만 확인: 중간 실패 시 구버전과 신버전이 섞인다.
- 기존 목록 전체 삭제 후 import: 실패 순간 전원의 가입이 막힌다.
- JSON을 앱이 런타임에서 직접 읽기: 재배포·재시작·백업 후 기준 데이터가 불명확해진다.

**Sources**:

- https://orm.drizzle.team/docs/transactions

## 5. 가입 허용 판단과 중복 방지

**Decision**: 가입 화면은 공통 초대 코드를 별도 요청으로 먼저 검증한다. 활성 전체 프로필
배치가 없으면 `profile_batch_not_ready`로 멈추고, 있을 때만 닉네임과 PIN 단계를 연다.
최종 가입 요청에서도 초대 코드와 활성 배치를 다시 검증하고, 활성 배치의 별칭 키로
프로필을 찾는다. 없으면 `nickname_not_invited`로 가입을 중단한다. 프로필 선점,
participant 생성, PIN 해시, conversation avatar 생성,
현재 avatar 연결을 하나의 트랜잭션으로 처리한다.

**Rationale**: 활성 프로필 별칭이 가입 허용 목록이 되므로 별도의 중복 회원 목록을
동기화할 필요가 없다. DB 고유 제약이 동시 가입을 최종 차단한다. 구체적인
허용 에러는 유효한 초대 코드를 아는 사용자에게만 보여 명단 열거 위험을 줄인다.

**Alternatives considered**:

- 미매칭 닉네임에 임시 아바타 제공: 새로운 가입 정책과 정면으로 충돌한다.
- 앱 메모리의 allowlist: 재시작·다중 인스턴스·배치 갱신에서 일관되지 않다.
- 프로필 선점과 계정 생성을 분리: 중간 실패 후 고아 상태가 남는다.

## 6. 결정적 프로필과 다양성

**Decision**: 원본 HMAC, 소스 버전, 생성기 버전을 입력으로 하고 형용사, 명사,
장비, 상태, 캐릭터 특성별로 독립된 해시 네임스페이스를 사용한다. 각 사용자의
확정 결과를 배치 import 시점에 저장하고, 신규 사용자 추가로 기존 결과를 재배치하지
않는다. 전체 조합 중복은 저장 전 검증하고 다른 후보로만 조정한다.

**Rationale**: 가입 시 다시 뽑지 않으므로 언제 접속해도 같은 결과가 나온다. 특성별
독립 선택은 후보 종류가 늘어도 다른 특성을 연쇄적으로 바꾸지 않는다. 화면 렌더링은
설치된 DiceBear Pixel Art 스타일을 서버 안에서 사용해 외부 아바타 API에 의존하지 않는다.

**Alternatives considered**:

- 가입 때마다 랜덤 선택: 재접속 결과가 바뀐다.
- 전체 사용자 정렬 순서로 강제 재배치: 한 명 추가가 기존 전원의 결과를 바꿀 수 있다.
- 외부 DiceBear HTTP API: 외부 요청과 가용성·개인정보 경계가 추가된다.

**Sources**:

- https://www.dicebear.com/styles/pixel-art/

## 7. 공개 연출과 통신 방식

**Decision**: 가입은 기존 `POST /api/participants/register`의 일반 JSON 응답으로 완료한다.
응답에 확정 프로필이 있으면 클라이언트가 3~5초 동안 연출용 후보와 문구를
자체 타이머로 전환한 뒤 서버가 준 확정 결과로 멈춘다. 움직임 축소에서는 빠른
후보 전환을 생략한다.

**Rationale**: Next.js Route Handler는 표준 Request/Response API로 POST 처리를 제공한다.
현재 가입은 이미 Route Handler이며 분석은 사전에 끝난다. 연출을 위해 SSE를 추가하면
서버 연결·타임아웃·재접속 상태만 늘어난다.

**Alternatives considered**:

- SSE: 전송할 실제 서버 진행 상태가 없다.
- 의도적으로 가입 API 응답을 5초 지연: 불필요한 연결 점유와 재시도 위험이 생긴다.
- 연출용 후보를 서버에 저장: 최종 결과와 관계없는 쓰레기 데이터가 쌓인다.

**Sources**:

- https://nextjs.org/docs/app/getting-started/route-handlers
- https://nextjs.org/docs/app/guides/backend-for-frontend

## 8. 검증과 운영 게이트

**Decision**: 임시 SQLite 픽스처로 전원 선택·시스템 제외·별칭 병합을 테스트한다.
실제 배치에서는 `unmatched=[]`, 충돌 검토 목록 비어 있음, HMAC 활성, 프로필 수=승인된
별칭 병합 후 고유 참가자 수, 모든 원본 행의 포함 여부, 원문 필드 부재, 닉네임 키
고유성을 가져오기 전에 검증한다. 운영자는 검토 목록이 있으면 별칭 파일을 수정해 전체
분석을 다시 실행한다. PostgreSQL import 후 새
배치를 활성화하기 전에 백업하고, 실패 시 이전 배치를 유지한다.

**Rationale**: 화면보다 전원 누락과 잘못된 별칭 병합이 더 큰 위험이다. 운영 전 실제
인원 수와 프로필 항목을 사람이 한 번 보는 절차를 둔다.

**Alternatives considered**:

- import 후에만 누락 확인: 이미 가입 허용 목록이 잘못 바뀌었을 수 있다.
- 운영자 검토 생략: 자동 유사도 판단이 다른 사람을 합친 경우를 발견하기 어렵다.

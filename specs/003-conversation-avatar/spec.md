# Feature Specification: 대화 기반 개발자 아바타

**Feature Branch**: `codex/conversation-avatar`

**Created**: 2026-08-30

**Status**: Draft

**Input**: User description: "단톡방에 있는 닉네임만 가입할 수 있고, 가입 중 대화 기반 아바타를 만든다. 기다리는 동안 랜덤 프로필과 `~하는 중` 문구가 계속 바뀌는 연출을 보여 준다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 승인된 닉네임으로 나만의 아바타 만들기 (Priority: P1)

단톡방 참가자 명단에 등록된 닉네임의 사용자는 가입 과정에서 행사 전에 미리 분석·확정해 둔 대화 기반 픽셀 캐릭터와 개발자 프로필을 받는다. 가입 시에는 대화 원문을 다시 분석하지 않고 승인된 닉네임과 완성된 프로필을 연결한다. 프로필은 근거가 있을 때 형용사와 개발자스러운 명사를 조합한 클래스, 장비, 상태, 짧은 표시용 해시로 구성된다.

**Why this priority**: 대화 기록이 나만의 결과로 바뀌는 경험이 이 기능의 핵심이다. 이 결과가 있어야 서로의 캐릭터를 비교하고 공유하는 재미도 생긴다.

**Independent Test**: 완성된 사전 프로필이 있는 승인 닉네임으로 가입해 공개 연출과 최종 프로필을 확인하고, 다시 접속했을 때 같은 결과가 나오는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 운영자가 승인한 단톡방 닉네임과 사전 생성된 프로필이 있는 사용자, **When** 해당 사용자가 닉네임과 PIN을 입력해 가입하면, **Then** 완성된 프로필이 계정에 연결되고 공개 연출 후 로비에 입장한다.
2. **Given** 같은 프로필 입력과 같은 생성 규칙 버전, **When** 참가자가 여러 번 로그인하거나 페이지를 새로고침하면, **Then** 클래스, 장비, 기본 상태와 캐릭터 모양이 바뀌지 않는다.
3. **Given** 프로필 생성이 완료된 참가자, **When** 최종 프로필이 공개되면, **Then** 시스템은 `initializing player`, `resolving developer traits`, `equipping ...`, `PLAYER READY` 순서의 짧은 터미널 형식 연출을 마친 뒤 확정된 결과에서 멈춘다.
4. **Given** 처음 가입하는 사용자, **When** 공통 초대 코드를 입력하면, **Then** 서버가 초대 코드를 먼저 확인한 뒤에만 닉네임과 PIN 입력 단계로 이동하며 최종 가입 요청에서도 초대 코드를 다시 검증한다.

---

### User Story 2 - 결과를 눌러 보고 공유하기 (Priority: P2)

참가자는 캐릭터 또는 프로필 카드를 눌러 이스터에그 상태 문구를 바꾸어 볼 수 있다. 결과는 웃기지만 해당 참가자를 조롱하거나 민감한 대화 습관을 노출하지 않는다.

**Why this priority**: 아바타를 한 번 보고 끝내는 장식이 아니라, 모임에서 서로 보여 주고 얘깃거리가 되게 한다.

**Independent Test**: 프로필 카드만 표시한 상태에서 마우스, 터치, 키보드로 상호작용하고 상태 문구가 읽을 수 있는 방식으로 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 개발자 프로필이 표시된 상태, **When** 참가자가 캐릭터를 클릭하거나 키보드로 활성화하면, **Then** `tests passed`, `works on my machine`, `node_modules is too heavy` 같은 승인된 문구 중 하나가 표시된다.
2. **Given** 작은 휴대폰 화면 또는 키보드만 사용하는 참가자, **When** 카드를 탐색하고 활성화하면, **Then** 프로필 정보가 잘리지 않고 상태 변화를 인식할 수 있다.
3. **Given** 움직임 축소를 요청한 참가자, **When** 아바타를 처음 표시하면, **Then** 긴 자동 애니메이션 없이 완성된 프로필을 바로 확인할 수 있다.

---

### User Story 3 - 내 프로필이 공개되는 순간 즐기기 (Priority: P1)

승인된 사용자는 이미 완성된 프로필을 바로 보는 대신, 3~5초 동안 여러 개의 랜덤 픽셀 캐릭터와 임시 클래스·장비 조합이 빠르게 바뀌는 공개 연출을 본다. 그 아래에는 `새벽 커밋 흔적 찾는 중`, `러버덕에게 의견 묻는 중`, `장비 슬롯 정리하는 중` 같은 짧은 문구가 계속 바뀐다. 회전하는 프로필은 공개 연출일 뿐 저장되거나 최종 결과로 사용되지 않고, 연출이 끝나면 사전에 확정된 결과로 멈춘다.

**Why this priority**: 실제 분석은 미리 끝내 안정적으로 운영하되, 참가자에게는 `내 결과가 뭐지?`라는 기대감을 남기는 것이 중요하다.

**Independent Test**: 사전 프로필이 있는 승인 닉네임으로 가입해, 랜덤 후보 프로필과 문구가 3~5초 동안 바뀌고 연출 종료 시 미리 확정된 결과에서 멈추는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 사전 프로필이 있는 승인 닉네임, **When** 사용자가 가입하면, **Then** 3~5초 사이에 최소 3종 이상의 임시 프로필 조합과 최소 3종 이상의 `~하는 중` 문구를 본 뒤 확정 프로필을 본다.
2. **Given** 공개 연출이 진행 중인 상태, **When** 랜덤 후보 프로필이 표시되면, **Then** 후보는 저장되거나 사용자의 최종 결과로 표시되지 않는다.
3. **Given** 공개 연출 중 페이지를 새로고침하거나 잠시 연결이 끊긴 참가자, **When** 다시 접속하면, **Then** 중복 계정이나 중복 프로필을 만들지 않고 연출을 다시 보거나 확정 프로필로 이동한다.
4. **Given** 아직 검증된 전체 프로필 배치가 활성화되지 않은 행사, **When** 사용자가 올바른 초대 코드를 확인하면, **Then** 닉네임·PIN 단계로 이동하지 않고 전체 프로필을 준비 중이라고 안내하며 계정이나 임시 프로필을 만들지 않는다.

---

### User Story 4 - 대화를 노출하지 않고 프로필 갱신하기 (Priority: P3)

운영자는 행사 전에 아카이브의 모든 비시스템 대화 참여자를 개인별로 미리 분석하고, 대화 원문을 행사 서비스로 옮기지 않은 채 요약 특징과 확정된 개발자 프로필을 저장한다. 메시지가 하나라도 있는 모든 참여자의 프로필과 별칭 병합 결과를 운영자가 검토한 뒤에 가입을 연다. 별칭이 애매하면 자동으로 연결하지 않고 운영자의 확인 대상으로 남긴다.

**Why this priority**: 새 대화가 추가될 때 다시 만들 수 있어야 하지만, 원문이 행사 서비스와 배포 경로에 남는 구조는 피해야 한다.

**Independent Test**: 원문이 있는 아카이브와 행사 서비스를 분리한 상태에서 요약 프로필 갱신을 수행한 뒤, 행사 서비스와 전달 산출물에 대화 원문이 없는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 아카이브에 비시스템 사용자의 대화 기록이 있는 상태, **When** 운영자가 행사 전 전체 사전 분석을 실행하면, **Then** 메시지가 하나 이상인 모든 참여자에 대해 활동 시간대, 대화량, 활동 규칙성, 평균 길이, 질문·웃음·링크·첨부·기술 주제 경향을 요약한 값과 확정 프로필만 행사 서비스에 전달된다.
2. **Given** 같은 정규화 닉네임을 가진 원본 사용자 행이 둘 이상이거나 서로 충돌하는 별칭, **When** 갱신이 실행되면, **Then** 시스템은 이들을 자동 병합하지 않고 원본 사용자 ID, 표시 닉네임, 메시지 수가 포함된 별도 검토 목록을 만든 뒤 import를 중단한다.
3. **Given** 같은 요약 입력과 같은 생성 규칙 버전, **When** 운영자가 갱신을 다시 실행하면, **Then** 각 참가자의 결과는 유지되고 새 참가자의 추가가 기존 참가자의 결과를 바꾸지 않는다.
4. **Given** 운영자가 충돌 검토 목록을 확인한 상태, **When** 같은 사람으로 합칠 항목을 승인해 별칭 규칙을 수정하고 분석을 다시 실행하면, **Then** 승인된 항목만 하나의 프로필로 병합되고 산출물에서 병합된 원본 별칭과 사용자 행을 확인할 수 있다.

### Edge Cases

- 닉네임의 공백, 대소문자, 특수문자가 다르더라도 승인된 정규화 규칙으로 유일하게 판단되면 같은 사람으로 매칭한다.
- 별칭이 두 프로필에 걸치거나 같은 정규화 닉네임을 가진 원본 사용자 행이 둘 이상이면 자동 매칭하지 않고 별도 검토 목록에 남긴다.
- 승인 명단에 없는 닉네임이면 계정과 PIN을 생성하지 않고 가입을 거절한다.
- 검증된 전체 프로필 배치가 아직 활성화되지 않았으면 초대 코드를 확인한 뒤 전체 프로필 준비 중임을 알리고 닉네임·PIN 단계와 가입을 열지 않는다.
- 승인된 닉네임이지만 대화량이 적어 근거 있는 특징을 만들 수 없으면 형용사·명사 같은 해당 필드를 비워 두고 화면에는 `—`로 표시한다. 자료가 없는데 성격이나 성향을 추측해 채우지 않고, 닉네임 기반 임시 아바타로도 대체하지 않는다.
- 이미 가입된 닉네임으로 새 PIN을 설정하려고 하면 새 계정을 만들지 않고 기존 로그인 흐름으로 안내한다.
- 공개 연출은 실제 분석 진행률을 표시하는 것이 아니므로, 숫자 진행률이나 예상 완료 시각을 표시하지 않는다.
- 움직임 축소 설정이 켜져 있으면 랜덤 프로필을 빠르게 바꾸지 않고, 정적인 대기 표시와 읽을 수 있는 상태 문구를 제공한다.
- 두 참가자가 같은 형용사나 명사 후보를 갖더라도 전체 클래스+장비 조합이 반복되지 않도록 다양성 규칙을 적용한다. 후보 공간이 부족한 경우에만 중복을 허용한다.
- 요약 프로필 갱신이 실패하거나 일부만 전달되면 이전에 완성된 프로필을 유지하고 운영자에게 실패 대상을 알린다.
- 표시용 해시가 같더라도 사용자 식별이나 인증에 사용하지 않고, 프로필 원본을 유추할 수 있는 정보도 담지 않는다.
- 대화 프로필이 교체되어도 이전 아바타와 현재 아바타를 구분할 수 있어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 참가자와 유일하게 매칭된 승인 상태의 대화 요약 프로필이 있으면 그 프로필을 아바타 생성 입력으로 사용해야 한다.
- **FR-002**: 시스템은 대화 요약 프로필을 활동 시간대, 대화량, 활동 규칙성, 평균 메시지 길이, 질문, 웃음, 링크, 첨부, 기술 주제 경향을 포함한 요약 특징으로 표현해야 한다.
- **FR-003**: 시스템은 근거가 있는 요약 특징에서 형용사 후보와 개발자 명사 후보를 독립적으로 만들고 각 목록에서 하나씩 골라 클래스를 구성해야 한다. 근거 있는 후보가 없으면 해당 목록과 확정 필드를 비워 두어야 한다.
- **FR-004**: 클래스 명사 후보에는 CSS Wizard, Bug Hunter, Type Guardian, Runtime Ranger, API Alchemist, Pixel Pusher, Legacy Survivor, Merge Conflict Resolver처럼 행사 분위기에 맞는 장난스러운 개발자 역할이 포함될 수 있어야 한다.
- **FR-005**: 시스템은 클래스와 독립적으로 장비, 기본 상태, 이스터에그 상태 문구, 픽셀 캐릭터 조합을 결정해야 한다.
- **FR-006**: 장비 후보에는 러버덕, 커피, 기계식 키보드, 노트북, 빨간 에러 로그, 초록색 테스트 체크, 무한히 열린 브라우저 탭, 정체불명 USB처럼 알아볼 수 있는 개발자 소품이 포함되어야 한다.
- **FR-007**: 같은 요약 입력과 같은 생성 규칙 버전은 언제나 같은 프로필 결과를 만들어야 한다.
- **FR-008**: 시스템은 새 참가자가 추가되거나 다른 참가자의 프로필이 갱신되어도 기존 참가자의 확정된 결과를 재배치하지 않아야 한다.
- **FR-009**: 시스템은 선택 가능한 조합이 남아 있는 한 초기 행사 참가자 간에 전체 클래스+장비 조합이 반복되지 않도록 해야 한다.
- **FR-010**: 시스템은 프로필에 PLAYER 닉네임, CLASS, ITEM, STATUS, 짧은 HASH를 표시해야 한다. 근거가 없어 확정되지 않은 CLASS 값은 추측으로 채우지 않고 `—`로 표시해야 한다.
- **FR-011**: 표시용 해시는 대화 원문이나 내부 프로필 식별자를 역추적할 수 없어야 하며, 인증·권한 판단에 사용해서는 안 된다.
- **FR-012**: 시스템은 첫 표시 시 터미널 형식의 짧은 공개 순서를 제공하고, 움직임 축소 설정에서는 연출을 건너뛰거나 최소화해야 한다.
- **FR-013**: 참가자는 마우스, 터치, 키보드로 캐릭터 카드를 활성화해 승인된 이스터에그 상태 문구를 바꾸어 볼 수 있어야 한다.
- **FR-014**: 대화 원문은 아카이브 환경 밖으로 이동하거나 행사 서비스, 배포 이미지, 소스 저장소, 운영 로그에 저장되어서는 안 된다.
- **FR-015**: 아카이브에서 행사 서비스로 전달되는 깨끗한 산출물은 개인별 요약 특징, 복원할 수 없는 안정적인 표식자, 생성 규칙 버전, 승인된 별칭과 병합된 원본 행 개수로 제한해야 한다. 원본 카카오 user ID와 충돌 검토 목록은 아카이브 환경과 서버 전용 승인 파일 밖으로 이동해서는 안 된다.
- **FR-016**: 명단에 없던 고유 닉네임 사용자는 전체 분석 대상에 자동 포함하되, 같은 정규화 닉네임을 가진 원본 사용자 행이 둘 이상이거나 별칭이 충돌하면 자동 병합하지 않고 별도 검토 목록을 만들어야 한다. 병합은 운영자가 승인해 별칭 규칙에 기록한 경우에만 허용해야 한다.
- **FR-017**: 시스템은 승인된 단톡방 닉네임 또는 별칭과 유일하게 매칭되는 사용자에게만 새 계정 생성을 허용해야 한다.
- **FR-018**: 승인 명단에 없거나 유일하게 매칭되지 않는 닉네임은 계정, PIN 인증 정보, 임시 아바타를 생성하지 않고 가입을 거절해야 한다.
- **FR-019**: 승인된 닉네임의 신규 가입은 행사 전에 생성되고 운영자가 승인한 대화 기반 프로필이 있을 때만 완료되어야 하며, 닉네임 기반 임시 아바타로 대체해서는 안 된다.
- **FR-020**: 승인된 닉네임과 완성된 프로필의 연결이 확인되면 시스템은 랜덤 픽셀 캐릭터, 임시 클래스, 임시 장비가 3~5초 동안 반복해 교체되는 공개 연출을 표시해야 한다.
- **FR-021**: 대기 화면은 `새벽 커밋 흔적 찾는 중`, `러버덕에게 의견 묻는 중`, `장비 슬롯 정리하는 중` 같은 짧고 장난스러운 `~하는 중` 문구를 반복해 바꾸어야 한다.
- **FR-022**: 대기 중 표시되는 후보 프로필과 문구는 연출용으로만 사용하며, 저장·공유·표시용 해시 생성에 포함하지 않아야 한다.
- **FR-023**: 공개 연출이 실제 분석 진행률인 것처럼 임의의 완료 퍼센트나 예상 완료 시각을 표시해서는 안 된다.
- **FR-024**: 공개 연출 중 새로고침·재접속이 발생해도 같은 확정 프로필을 사용하고, 같은 닉네임의 중복 계정과 중복 프로필을 만들지 않아야 한다.
- **FR-025**: 시스템은 공통 초대 코드를 서버에서 먼저 확인하고 검증된 전체 프로필 배치가 활성 상태일 때만 닉네임·PIN 입력 단계를 열어야 한다. 배치가 없으면 `profile_batch_not_ready` 안내를 제공하고 계정·PIN·임시 프로필을 만들지 않아야 한다. 활성 배치가 있으면 미매칭 닉네임은 `nickname_not_invited`로 거절하고, 최종 가입 요청에서는 초대 코드와 활성 배치를 다시 검증해야 한다.
- **FR-026**: 움직임 축소 설정에서는 랜덤 프로필의 빠른 전환을 중지하고, 정적인 대기 표시와 읽을 수 있는 상태 문구로 같은 공개 단계를 전달해야 한다.
- **FR-027**: 운영자는 가입을 열기 전에 아카이브 환경에서 분석기가 만든 충돌 검토 목록과 병합 내역을 확인해야 한다. 애매한 항목은 관리자 웹 화면에서 직접 편집하지 않고 Git에 포함되지 않는 서버 전용 별칭 규칙 파일을 수정한 뒤 전체 분석을 다시 실행하며, 검토 목록이 비어 있는 배치만 import할 수 있어야 한다.
- **FR-028**: 사전 분석과 프로필 갱신은 행사 서비스의 가입 요청과 분리되어야 하며, 실시간 대화 서버 연결에 의존하지 않아야 한다. 갱신 실패 시에는 이전에 완성된 프로필을 유지하고 재시도할 수 있어야 한다.
- **FR-029**: 기존 계정에 닉네임 기반 임시 아바타가 있다면 다음 로그인에서 사전에 확정된 대화 기반 프로필로 교체한 뒤 로비에 진입시켜야 하며, 기존 계정과 답변은 유지해야 한다.

### Key Entities

- **대화 요약 프로필**: 한 대화 참여자의 원문 없는 활동 특징, 복원 불가능한 표식자, 생성 규칙 버전, 산출 시점을 담는다.
- **별칭 매칭**: 대화방에서 쓰던 한 개 이상의 이름과 행사 계정을 연결하는 서버 전용 운영자 승인 규칙이다. 충돌 후보는 아카이브 환경의 검토 목록에 남고, 활성 배치에는 승인된 별칭만 들어간다.
- **개발자 아바타 프로필**: 참가자의 근거 있는 형용사·명사 후보, nullable 확정 클래스, 장비, 상태 문구 목록, 표시용 해시, 캐릭터 선택값, 생성 규칙 버전을 담는다.
- **승인 참가자**: 새 계정을 만들 수 있는 단톡방 닉네임과 별칭, 사용 여부, 현재 가입·생성 상태를 담는다.
- **클라이언트 공개 상태**: 확정 프로필을 받은 브라우저에서만 `idle`, `shuffling`, `ready` 상태를 관리한다. 공개 시작·완료 시점과 연출 중 후보 프로필은 서버나 DB에 저장하지 않는다.
- **아바타 버전 이력**: 한 참가자에게 적용됐던 기존 임시 결과 또는 대화 기반 결과의 종류, 생성 규칙 버전, 적용 시점, 현재 사용 여부를 담는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 아카이브의 비시스템 사용자 중 메시지가 하나 이상인 모든 원본 사용자 행이 정확히 하나의 확정 프로필 또는 충돌 검토 항목에 포함된다. 검토가 끝난 활성 배치에서는 별칭 병합 후 고유 참가자 수와 확정 프로필 수가 일치하며, 원본 사용자 행 수와 프로필 수는 달라도 된다.
- **SC-002**: 같은 입력과 같은 생성 규칙 버전으로 100번 반복 생성했을 때 각 참가자의 프로필 결과가 100% 일치한다.
- **SC-003**: 새 참가자 또는 새 대화 프로필을 추가한 후에도 기존에 확정된 참가자 결과의 100%가 이전과 같다.
- **SC-004**: 선택 가능한 조합 수가 전체 참여자 수보다 많은 조건에서 전체 참여자의 클래스+장비 조합이 중복되지 않는다.
- **SC-005**: 승인 명단에 없는 닉네임으로 가입을 20번 시도했을 때 계정, PIN 인증 정보, 아바타가 생성된 경우가 0건이다.
- **SC-006**: 프로필 갱신 전달물과 행사 서비스의 저장 내용을 검사했을 때 대화 원문, PIN, 초대 코드, 세션 값이 0건이다.
- **SC-007**: 360px 너비의 화면과 키보드 전용 조작에서도 모든 프로필 필드를 읽고 상태 문구를 변경할 수 있다.
- **SC-008**: 움직임 축소 설정을 활성화한 참가자는 빠른 후보 전환 없이도 1초 안에 프로필 공개를 준비 중임을 알 수 있다.
- **SC-009**: 매칭 충돌이나 갱신 실패가 있을 때 운영자가 영향받은 대상과 다음 조치를 확인할 수 있고, 이전에 정상 생성된 프로필은 손상되지 않는다.
- **SC-010**: 사전 프로필이 있는 가입 시험에서 공개 화면이 1초 안에 나타나고, 3~5초 동안 서로 다른 후보 프로필과 `~하는 중` 문구가 각각 3종 이상 표시된 뒤 확정 결과로 멈춘다.
- **SC-011**: 사전 프로필이 준비된 승인 닉네임 가입 요청의 95%가 2초 안에 서버에서 완료되고, 사용자는 제출 후 1초 안에 즉각적인 준비 상태를 보며 95%가 7초 안에 공개 연출과 계정 생성을 완료한다.
- **SC-012**: 공개 연출 중 새로고침·재접속을 20회 반복해도 한 승인 닉네임에 대한 계정과 최종 프로필은 각각 1개만 생성된다.

## Assumptions

- 초기 대상은 아카이브에서 시스템 계정으로 표시되지 않고 메시지가 하나 이상 있는 모든 단톡방 참가자다. 사전 분석으로 만든 전체 닉네임과 승인된 별칭 목록이 새 계정 생성의 허용 목록이 된다.
- 기존의 공통 초대 코드, 닉네임, 개인 PIN 방식을 계속 사용한다. 신규 가입 화면은 초대 코드 확인과 닉네임·PIN 입력의 두 단계로 나누지만 새로운 로그인 수단을 추가하지 않는다.
- 대화 요약과 전체 참여자의 확정 프로필은 가입을 열기 전에 행사 서비스와 분리된 아카이브 환경에서 일괄 생성된다. 행사 서비스는 가입 중 아카이브에 접속하거나 대화를 분석하지 않는다.
- 대화 특징은 사람의 성격을 진단하거나 평가하는 용도가 아니라, 모임용 캐릭터를 만드는 가벼운 통계 입력으로만 사용한다.
- 형용사, 명사, 장비, 상태 문구 목록은 행사에 맞게 미리 검토된 내용으로 구성한다.
- `002` 번은 기존 작업의 진행자 결과 표시 기능에 예약되어 있어, 이 기능은 `003` 번을 사용한다.

## Out of Scope

- 행사 서비스가 카카오 대화 서버를 실시간으로 조회하는 기능
- 가입 요청 도중에 대화 원문을 분석하거나 백그라운드 작업을 새로 시작하는 기능
- 공개 연출을 위한 실시간 스트리밍 또는 서버 진행률 전송
- 승인 명단에 없는 사용자를 임시 아바타로 가입시키는 기능
- 대화 원문, 개별 메시지, 정확한 메시지 수를 참가자 화면에 공개하는 기능
- 자동 성격 진단, 감정 판단, 참가자 순위나 우열 표시
- 참가자가 확정된 클래스나 장비를 임의로 다시 뽑는 기능
- 아바타 결과를 공개 순위표, 전적, 보상 시스템으로 확장하는 기능

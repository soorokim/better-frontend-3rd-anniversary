# Quickstart & Validation: 진행자 결과 발표 화면

이 문서는 구현 뒤 새 테스트 데이터베이스에서 진행자 조작 화면과 프로젝터 화면을 처음부터
검증하는 기준이다. 운영 답변이나 운영 발표 상태를 테스트에 사용하지 않는다.

## Prerequisites

- `001-event-core-flow`의 참가자 등록, 답변 저장, 관리자 로그인과 PIN 복구가 동작해야 한다.
- Node.js 22와 프로젝트 의존성이 설치되어 있어야 한다.
- 운영 volume과 분리한 PostgreSQL 테스트 데이터베이스가 있어야 한다.
- 테스트용 행사에 공개 질문 1개와 관리자 계정 1개를 준비한다.

## Setup and Automated Gates

```bash
npm ci
npm run typecheck
npm run lint
npm test
TEST_DATABASE_URL=<isolated-url> DATABASE_URL=<isolated-url> npm run test:integration
npm run build
npm run test:e2e
```

기대 결과:

- 발표 세션과 항목 마이그레이션이 빈 데이터베이스와 기존 데이터베이스 모두에 적용된다.
- 단위, 실제 PostgreSQL 통합, Playwright 테스트가 모두 통과한다.
- 기존 참가자 등록·답변 저장과 관리자 PIN 복구 테스트도 계속 통과한다.
- 운영 빌드에 진행자 조작, 발표 화면과 세 개의 관리자 계약이 포함된다.

## Test Data

같은 행사와 질문에 다음 상태를 만든다.

| 참가자 | 답변 상태 | 내용 특징 |
|--------|-----------|-----------|
| 픽셀고양이 | 제출 | 짧은 한글 답변 |
| 자바스크립트요정 | 제출 | 줄바꿈과 이모지 포함 |
| 리액트탐험가 | 제출 | URL과 긴 공백 없는 영문 포함 |
| CSS마법사 | 미제출 | 답변 없음 |

긴 답변 표시 검증에서는 별도 참가자에게 1,000자 경계 답변을 추가한다. 모든 데이터는 격리
테스트 DB에만 만들고 검증 뒤 전체 테스트 DB를 제거한다.

## Scenario 1: Authorization and Data Boundary

1. 로그아웃 상태와 참가자 세션으로 진행자·발표 화면 및 세 계약에 접근한다.
2. 관리자 로그인 뒤 같은 주소를 다시 연다.
3. 조작 화면 응답과 발표 화면 응답을 비교한다.

기대 결과:

- 비관리자는 답변 전문이나 진행 상태를 한 건도 받지 못한다.
- 관리자는 조작 화면에서만 답변 후보, 닉네임, 캐릭터와 제출 현황을 본다.
- 익명 발표 응답에는 `author` 필드, 후보 목록, 참가자 ID와 답변 ID가 존재하지 않는다.
- 모든 응답은 `no-store, private`이며 상태 변경은 Origin과 CSRF 검증 없이는 거부된다.

## Scenario 2: First Anonymous Presentation

1. `/admin/presenter`에서 전체 4명, 제출 3명, 미제출 1명을 확인한다.
2. 프로젝터용 발표 화면을 새 창에 연다.
3. 아직 공개하지 않은 답변 무작위 선택을 실행한다.
4. 발표 화면이 익명 답변으로 바뀐 뒤 작성자를 공개한다.

기대 결과:

- 첫 답변 선택과 발표 화면 전환을 1분 안에 완료할 수 있다.
- 최초 공개는 항상 익명이며 닉네임과 캐릭터가 응답에도 없다.
- 작성자 공개 뒤에만 정확한 닉네임과 캐릭터가 답변과 함께 나타난다.
- 조작 성공과 발표 화면 반영 사이는 정상 연결에서 5초를 넘지 않는다.

## Scenario 3: Order, Navigation, and Random Exhaustion

1. 무작위 선택을 세 번 실행하고 각 답변과 공개 순서를 기록한다.
2. 네 번째 무작위 선택을 시도한다.
3. 이전·다음으로 이동한 뒤 완료된 답변 하나를 직접 재선택한다.

기대 결과:

- 세 제출 답변이 중복 없이 정확히 한 번씩 선택된다.
- 모든 답변을 본 뒤 자동 반복하지 않고 완료 상태와 다시 시작 방법을 안내한다.
- 이전·다음은 최초 공개 순서를 따르며 범위를 벗어난 이동은 상태를 바꾸지 않는다.
- 직접 재선택은 허용되며 다른 답변의 순서와 완료 상태를 잃지 않는다.
- 답변을 바꾸거나 이동할 때 작성자 공개 상태는 안전하게 익명으로 돌아간다.

## Scenario 4: Snapshot and New Submission

1. 한 답변을 공개한 채 참가자가 해당 원본 답변을 수정한다.
2. 현재 진행자·발표 화면을 확인한다.
3. 같은 답변을 목록에서 직접 재선택한다.
4. 미제출 참가자가 새 답변을 저장한다.

기대 결과:

- 말하는 중인 현재 슬라이드는 원본 수정 때문에 갑자기 바뀌지 않는다.
- 같은 답변을 명시적으로 재선택하면 최신 성공본으로 스냅샷이 갱신된다.
- 새 답변은 기존 공개 순서와 현재 슬라이드를 바꾸지 않고 5초 안에 미공개 후보로 추가된다.
- 어떤 경우에도 원본 Answer의 작성자나 내용이 발표 기능에 의해 바뀌지 않는다.

## Scenario 5: Persistence and Concurrent Commands

1. 답변 두 개를 공개하고 두 번째 답변의 작성자를 공개한다.
2. 조작 화면과 발표 화면을 새로고침한다.
3. 앱 컨테이너를 재시작하고 다시 확인한다.
4. 두 관리자 창에서 서로 다른 진행 명령을 거의 동시에 실행한다.

기대 결과:

- 현재 답변, 두 답변의 최초 순서, 작성자 공개 여부와 revision이 복구된다.
- 컨테이너 재시작 뒤에도 같은 상태가 유지된다.
- 동시 명령은 순서 충돌이나 중복 항목 없이 직렬로 완료되고 revision이 각각 증가한다.
- 두 창은 다음 조회 안에 마지막으로 성공한 상태로 수렴한다.

## Scenario 6: Restart Without Answer Loss

1. 모든 답변을 공개한 상태에서 일반 조작으로 다시 시작을 시도한다.
2. 명시적인 확인 절차로 발표 초기화를 실행한다.
3. 참가자의 원본 답변 수와 내용을 초기화 전후 비교한다.

기대 결과:

- 확인 전에는 공개 이력이 사라지지 않는다.
- 확인 뒤 현재 슬라이드와 발표 항목만 대기 상태로 초기화된다.
- 원본 답변, 참가자와 캐릭터는 한 건도 삭제되거나 수정되지 않는다.
- revision은 되돌아가지 않고 증가해 오래된 화면이 초기화 전 상태를 덮지 못한다.

## Scenario 7: Projector Failure Recovery and Accessibility

1. 1,366×768 화면에서 1,000자 답변, 줄바꿈, URL, 이모지 답변을 각각 표시한다.
2. 키보드만으로 무작위 선택, 작성자 공개, 이전·다음과 발표 화면 진입을 수행한다.
3. 발표 화면의 네트워크를 끊었다가 다시 연결한다.
4. 관리자 세션을 폐기하고 다음 조회를 기다린다.

기대 결과:

- 답변이 다른 요소와 겹치거나 화면 밖으로 사라지지 않고 끝까지 읽을 수 있다.
- 모든 주요 동작에 텍스트 라벨, 보이는 포커스와 상태 안내가 있다.
- 연결 중에는 마지막 정상 슬라이드와 연결 상태가 보이고, 복구 뒤 5초 안에 최신 revision으로
  맞춰진다.
- 세션 폐기 뒤에는 새 답변을 탐색하지 않고 재인증을 안내한다.

## Implementation Validation (2026-08-30)

운영 서비스와 분리된 빌드 컨테이너, 빈 PostgreSQL volume에서 최종 검증했다. 브라우저
시나리오는 서로 상태를 이어 쓰므로 매 전체 실행 전에 테스트 DB를 새로 만들고 한 worker로
실행했다.

| 검증 | 결과 |
|------|------|
| 빈 DB 마이그레이션, seed, 마이그레이션 재실행 | 통과 |
| 단위 테스트 | 7 files, 44 tests 통과 |
| 실제 PostgreSQL 통합 테스트 | 12 files, 47 tests 통과 |
| 진행자·프로젝터 E2E | 3 tests 통과 |
| 기존 모바일 참가자·관리자·접근성 E2E | 7 tests 통과 |
| lint, typecheck, production build | 통과 |
| Docker 이미지 빌드와 health check | 통과 |

Scenario 1·2는 관리자 경계, 익명 응답에서 `author` 필드 자체가 빠지는지, 최초 무작위
공개와 작성자 공개를 단위·통합·브라우저 단계에서 확인했다. Scenario 3~6은 30개 답변을
중복 없이 모두 공개하고, 이전·다음 이동, 최초 순서를 유지한 직접 재선택, 늦은 제출 반영,
동시 명령 직렬화와 확인 뒤 초기화를 검증했다. 초기화 뒤에도 원본 참가자와 답변은 남았다.

Scenario 7은 1,366×768 프로젝터 화면에서 1,000자 답변, 줄바꿈, URL과 이모지를 표시하고
키보드 조작, 오프라인 중 마지막 슬라이드 유지, 온라인 복귀 직후 자동 재연결, 세션 만료 뒤
비공개 내용 제거까지 확인했다.

OpenAPI의 세 경로(`GET /api/admin/presentation`, `POST
/api/admin/presentation/commands`, `GET /api/admin/presentation/screen`)를 실제 route와
대조했다. 성공 응답 필드와 400·401·403·404·409 처리, `no-store, private`, Origin·CSRF
검증이 계약 및 통합 테스트와 일치했다.

E2E 종료 상태를 백업하고 별도 DB에 복원했을 때 참가자 30, 답변 30, 발표 항목 2, 세션 1,
현재 항목 1, revision 42가 모두 같았다. 앱 컨테이너 재시작 뒤에도 같은 값과 health 응답이
유지됐다. 검증이 끝난 뒤 테스트 컨테이너, DB volume과 임시 백업은 제거했다.

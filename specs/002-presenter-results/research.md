# Research: 진행자 결과 발표 화면

## Decision 1: 2초 간격의 관리자 전용 정기 조회

**Decision**: 진행자 조작 화면과 발표 화면은 서로 다른 조회 계약을 2초마다 호출한다. 모든
응답은 캐시하지 않고 단조 증가하는 `revision`을 포함한다. 쓰기 성공 직후에는 즉시 최신
상태를 반영하고 이후 정기 조회로 다른 창과 맞춘다.

**Rationale**: 동기화 소비자는 진행자 창과 프로젝터 창 정도이고 답변도 최대 30개다. 합계
초당 약 한 번의 작은 조회로 명세의 5초 반영 목표를 여유 있게 만족한다. 연결이 끊겨도 마지막
정상 슬라이드를 유지하고, 복구 뒤 영구 저장된 최신 revision을 읽으면 된다. 현재 배포 구조를
바꾸거나 장기 연결 상태를 관리할 필요도 없다. Next.js Route Handler의 현재 동작과 자체
호스팅 조건은 공식 [Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers),
[Self-Hosting](https://nextjs.org/docs/app/guides/self-hosting) 문서를 기준으로 확인했다.

**Alternatives considered**:

- SSE는 단방향 전달에 맞지만 변경 알림 원천, heartbeat, 프록시 buffering, 재연결과 세션
  만료 검증이 추가된다.
- WebSocket은 양방향 초저지연이 필요하지 않은 이번 범위보다 크다. 별도 서버 또는 custom
  server는 standalone 배포 구조까지 바꿀 수 있어 제외한다.
- 5초 정기 조회는 네트워크와 렌더링 지연이 겹치면 5초 목표를 넘을 여지가 있어 2초를 택한다.

## Decision 2: 질문별 발표 세션과 공개 답변 항목을 분리

**Decision**: `presentation_sessions`는 현재 항목, 작성자 공개 여부와 revision만 보관한다.
`presentation_items`는 실제로 한 번 이상 공개한 답변의 내용·닉네임·캐릭터 스냅샷과 최초
발표 순서를 보관한다. 답변이 항목에 존재하면 공개 완료로 본다.

**Rationale**: 아직 공개하지 않은 답변을 미리 복제하지 않아도 새 제출이 자연스럽게 후보에
들어온다. 발표 중 원본 답변이 수정돼도 현재 슬라이드는 바뀌지 않고, 진행자가 같은 답변을
다시 선택했을 때만 최신 성공본으로 스냅샷을 갱신할 수 있다. 원본 답변과 진행 상태도 섞이지
않는다.

**Alternatives considered**:

- 세션 한 행의 배열 또는 JSON에 모든 상태를 넣으면 답변 관계와 순서 유일성을 저장소가
  보장하기 어렵다.
- `answers`에 공개 여부를 넣으면 참가자 기록과 행사 진행 상태가 결합되어 원본 불변 조건을
  어긴다.
- 여러 발표 회차를 영구 보존하는 모델은 이번 행사에 필요하지 않다. 다시 시작은 명시적인
  초기화로 처리한다.

## Decision 3: 세션 행 잠금으로 진행 명령 직렬화

**Decision**: 모든 진행 상태 변경은 질문별 발표 세션을 준비한 뒤 해당 행을 잠그고 처리한다.
잠금 뒤 후보와 현재 상태를 다시 읽고, 스냅샷·순서·현재 항목을 바꾼 뒤 revision을 1 올려
같은 트랜잭션으로 완료한다.

**Rationale**: 두 창에서 무작위 선택을 거의 동시에 눌러도 같은 답변이나 같은 순서가 생기지
않는다. 먼저 완료된 명령 다음에 두 번째 명령이 최신 상태를 읽으며, 마지막으로 성공한
revision이 모든 창의 기준이 된다. 질문별 한 행만 잠그므로 30명 규모에서 비용도 작다.

**Alternatives considered**:

- 잠금 없는 last-write-wins는 현재 포인터는 남겨도 무작위 중복과 순서 충돌을 막지 못한다.
- `expectedRevision`을 요구하는 낙관적 잠금은 주 진행자 한 명의 보조 창에서 불필요한 충돌
  오류와 재시도를 만든다.
- 별도 분산 잠금이나 관리자 창 리더 선출은 현재 단일 저장소와 진행자 범위보다 크다.

## Decision 4: 조작용 응답과 프로젝터용 응답 분리

**Decision**: 조작 화면 조회는 제출 현황, 최신 답변 후보와 작성자 정보를 반환한다. 발표
화면 조회는 현재 질문, 현재 슬라이드 스냅샷과 revision만 반환한다. 익명 상태라면 작성자
필드 자체를 만들지 않는다.

**Rationale**: 작성자 정보를 내려받은 뒤 화면에서만 숨기는 방식은 실수로 DOM이나 개발자
도구에 남길 수 있다. 별도 allowlist DTO는 프로젝터가 아직 공개하지 않은 답변 목록이나 PIN
운영 정보까지 받는 일을 막는다.

**Alternatives considered**:

- 하나의 큰 응답을 두 화면이 함께 쓰면 편하지만 익명성과 최소 공개 경계가 약해진다.
- 공개용 임시 토큰 링크는 유출·회수·만료 정책이 새로 필요하다. 이번에는 기존 관리자 세션을
  사용하는 관리 브라우저만 발표 화면을 연다.

## Decision 5: 기존 관리자 인증과 단일 command 계약 재사용

**Decision**: 두 화면과 모든 조회는 기존 관리자 세션을 확인한다. 상태 변경은 Origin과 CSRF를
검증하는 단일 command 계약에서 `select_answer`, `select_random`, `set_author_visibility`,
`navigate`, `restart`만 허용한다. 응답은 모두 `no-store, private`로 제한한다.

**Rationale**: 별도 진행자 역할이나 인증 수단 없이 기존 유휴·절대 만료 정책을 그대로 쓸 수
있다. 명령을 allowlist로 제한하면 임의 필드 수정으로 불가능한 상태가 생기지 않고 인증,
검증과 트랜잭션 경계를 한곳에서 빠뜨리지 않게 된다.

**Alternatives considered**:

- 상태 필드를 임의로 받는 PATCH는 현재 항목, 스냅샷과 공개 여부가 서로 맞지 않는 조합을
  만들 수 있다.
- 명령별 endpoint는 의미는 분명하지만 인증·CSRF·오류 처리 중복이 커진다.
- 프로젝터 전용 비밀번호나 브라우저 저장 토큰은 관리할 비밀만 늘어난다.

## Decision 6: 실패 시 마지막 정상 슬라이드 유지

**Decision**: 조회 실패 중에는 마지막으로 받은 발표 슬라이드를 유지하고 연결 상태를 표시한다.
재시도 간격은 1초부터 최대 5초까지 늘리며, 온라인 복귀나 탭 재활성화 때 즉시 조회한다.
401·403이면 새 데이터 탐색을 중단하고 재인증을 안내한다.

**Rationale**: 일시적인 행사장 네트워크 문제로 프로젝터가 빈 화면이 되는 것보다 이미 공개한
내용을 유지하는 편이 진행 복구에 유리하다. 동시에 세션 만료 뒤에는 다음 비공개 답변으로
탐색할 수 없게 막는다.

**Alternatives considered**:

- 실패 즉시 빈 화면으로 바꾸면 공개 정보는 줄지만 진행 중인 대화가 불필요하게 끊긴다.
- 오류 중 계속 2초 요청을 보내면 장애 상황에서 의미 없는 요청이 쌓인다.

## Decision 7: 테스트 계층을 상태·계약·실제 두 창으로 분리

**Decision**: 단위 테스트는 명령 검증, 무작위 후보와 DTO redaction을 확인한다. 실제
PostgreSQL 통합 테스트는 권한·CSRF·스냅샷·행 잠금·원본 답변 불변을 검증한다. Playwright는
진행자와 발표 화면을 두 페이지로 열어 2초 동기화, 오프라인 복구, 키보드와 1,366×768 긴
답변 표시를 검증한다.

**Rationale**: 순수 상태 규칙과 DB 원자성, 실제 브라우저 동기화를 각각 가장 빠르고 정확한
계층에서 확인할 수 있다. 기존 참가자 답변과 관리자 PIN 복구 테스트도 함께 돌려 회귀를
막는다.

**Alternatives considered**:

- 모든 조건을 종단 테스트에 넣으면 동시성과 DB 불변 실패 원인을 찾기 어렵다.
- 단위 테스트만으로는 서버 권한과 실제 두 창 동기화 및 레이아웃을 증명할 수 없다.

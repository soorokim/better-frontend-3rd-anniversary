# Frontend Chat 3rd Anniversary Constitution

## Core Principles

### I. 행사 경험 우선
모든 기능은 프론트엔드 단톡방 3주년 모임의 참여와 진행을 직접 도와야 한다.
행사 전 작성, 행사 중 진행, 행사 후 기록 열람 중 어느 단계에도 쓰이지 않는 기능은
MUST 구현하지 않는다. 참가자의 입력 흐름과 진행자의 복구 수단은 시각적 연출보다
먼저 완성하고 검증한다. 기능의 가치는 구현 난이도나 화려함이 아니라 실제 모임에서
막힘없이 사용할 수 있는지로 판단한다.

### II. 모바일과 접근성 기본 보장
참가자용 핵심 기능은 작은 휴대폰 화면과 터치 입력에서 MUST 완전히 사용할 수 있어야
한다. 본문 가독성을 위해 픽셀 폰트는 제목, 짧은 라벨, 장식에만 사용하고 긴 한글에는
읽기 쉬운 글꼴을 사용한다. 모든 주요 동작은 명확한 텍스트 라벨, 키보드 포커스,
충분한 대비를 제공해야 한다. 애니메이션과 효과음은 기능 이해를 방해해서는 안 되며,
움직임 축소 설정과 음소거 상태를 존중해야 한다.

### III. 기록의 보호와 데이터 지속성
초대받은 참가자의 기록과 단톡방에서 가져온 내용은 공개 인터넷 콘텐츠로 취급하지
않는다. 서버는 초대 검증과 권한 검사를 MUST 수행하며, 클라이언트 화면을 숨기는 것만으로
접근을 제한해서는 안 된다. PIN과 관리자 비밀값은 평문으로 저장하거나 저장소에 커밋하지
않는다. 참가자가 제출한 기록과 행사 상태는 브라우저 저장소가 아닌 서버의 영구 저장소를
기준 데이터로 삼아야 하며, 컨테이너 재시작과 재배포 뒤에도 유지되어야 한다.

### IV. 재현 가능한 자체 호스팅
깨끗한 서버에서 저장소를 받은 사람이나 AI가 문서만 보고 서비스를 실행할 수 있어야
한다. 운영에 필요한 애플리케이션과 데이터베이스는 Docker Compose로 MUST 재현 가능해야
하며, 실행에 필요한 값은 `.env.example`에 이름과 용도를 설명한다. 비밀값과 운영 데이터는
이미지나 Git 저장소에 포함하지 않는다. 데이터베이스 변경은 버전 관리되는 마이그레이션으로
적용하고, 백업과 복구 절차를 실제 명령과 함께 문서화한다.

### V. 작고 복구 가능한 구현
기능은 독립적으로 확인할 수 있는 작은 구간으로 나누고, 각 구간은 명세와 완료 조건을
충족한 뒤 다음 구간으로 넘어간다. 회원가입, 파일 업로드, 실시간 소켓, 자유로운 캐릭터 이동
같은 복잡한 기능은 승인된 명세에서 필요성이 확인되기 전까지 MUST 추가하지 않는다.
행사 중 발생할 가능성이 있는 잘못된 입력, PIN 분실, 진행자의 문제 전환 실수는 관리자
화면에서 복구할 수 있어야 한다. 새 추상화나 서비스 분리는 현재 요구사항으로 정당화되어야
하며, 미래 가능성만을 이유로 추가하지 않는다.

## 기술 및 운영 제약

- 참가자 화면과 진행자 화면은 권한과 목적이 명확히 분리되어야 한다.
- 모든 입력은 서버 경계에서 검증하고, 오류는 사용자가 다음 행동을 알 수 있는 문장으로
  표시해야 한다.
- 운영 데이터의 삭제, 초기화, 전체 공개 전환은 명시적인 관리자 동작으로만 수행한다.
- 로그에는 PIN, 초대 코드, 세션 값, 비공개 답변 전문을 남기지 않는다.
- 핵심 흐름은 네트워크 지연과 페이지 새로고침을 견뎌야 하며, 현재 상태로 다시 진입할 수
  있어야 한다.
- 사용한 폰트, 아이콘, 픽셀 에셋은 배포 가능한 라이선스인지 확인하고 출처를 기록한다.
- 운영 배포 전에 데이터 백업과 복구를 최소 한 번 실제로 검증한다.

## 명세 기반 개발 절차

모든 기능 구간은 `spec.md`에서 사용자 시나리오와 성공 조건을 먼저 정의하고,
`plan.md`에서 기술 선택과 데이터 흐름을 정한 뒤, `tasks.md`의 의존 순서대로 구현한다.
요구사항이 불분명하면 계획이나 구현 전에 명세를 보완한다. 구현이 끝난 구간은 명세,
계획, 작업 목록과 실제 결과를 대조하고 남은 일을 기록해야 한다.

각 구간의 완료 검토에는 최소한 다음 항목이 포함되어야 한다.

- 대표 사용자 시나리오가 처음부터 끝까지 동작하는가
- 모바일 화면과 키보드 조작에서 핵심 기능을 사용할 수 있는가
- 권한 검사와 입력 검증이 서버에서도 적용되는가
- 재시작 또는 새로고침 뒤 데이터와 진행 상태가 보존되는가
- 실패 상황을 참가자 또는 진행자가 이해하고 복구할 수 있는가
- 설치, 환경변수, 마이그레이션 변경이 문서에 반영되었는가

명세 변경으로 이미 완료된 동작이 달라지면 관련 문서와 테스트를 같은 변경에서 갱신한다.
완료 조건을 충족하지 못한 항목은 다음 구간으로 숨겨 넘기지 않고 작업 목록에 남긴다.

## Governance

이 헌법은 프로젝트의 다른 계획과 구현 관행보다 우선한다. 새 기능 명세와 기술 계획은
각 원칙에 위배되지 않는지 확인해야 하며, 예외가 필요하면 이유, 범위, 복구 방안을 해당
계획에 기록한다.

헌법 수정은 변경 이유와 영향을 문서에 남기고 사용자의 승인을 받아야 한다. 버전은 의미론적
버전 규칙을 따른다. 원칙의 삭제나 의미 반전은 MAJOR, 새 원칙이나 실질적인 요구사항 추가는
MINOR, 의미를 바꾸지 않는 설명과 문구 수정은 PATCH로 올린다. 모든 수정은 상단의 Sync
Impact Report와 마지막 수정일을 함께 갱신한다.

각 기능의 계획 단계와 완료 단계에서 헌법 준수 여부를 검토한다. 복잡성을 추가한 구현은
어떤 현재 요구사항 때문에 필요한지 설명할 수 있어야 하며, 설명할 수 없으면 제거하거나
명세 승인 전 상태로 되돌린다.
